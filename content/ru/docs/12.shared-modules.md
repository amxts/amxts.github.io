Статус: готово. Поддельный сервер: `tests/shared-modules.test.ts` (два
плагина над одним menu-core и одним universal-config: меню, которое заводит
один, а показывает другой, условие, плейсхолдер и действия, вызванные
обратно, `preventDefault()` из другого плагина, поля меню на чтение и запись,
секция конфига, созданная в памяти одним и найденная другим, отсутствующий
владелец и ошибки сборки), а также `tests/menu-core.test.ts` и
`tests/nhnse-core.test.ts`, где menu-core и nhnse теперь ходят через это.
Настоящий сервер: `bun run test:server`.

У модуля в `as/modules/`, для которого есть плагин с тем же именем, -
плагин menu-core `as/menu-core.ts` и `~/modules/menu-core`, плагин
universal-config и `~/modules/universal-config` - **один экземпляр на
сервер**, экземпляр этого плагина. Все плагины пишут один и тот же импорт:

```ts
import * as menus from "~/modules/menu-core";
import * as ini from "~/modules/universal-config";

menus.addCondition("IS_ALIVE", (player) => player.isAlive);
menus.addAction("RESET_SCORE", (player) => resetScore(player));
menus.show(player, "MAIN_MENU", { resetHistory: true });

const menu = menus.find("MAIN_MENU");
if (menu != null) menu.hideExit = true;

ini.setBaseDir("nhnse");
const main = ini.section(ini.load("core.ini"), "MAIN");
```

В плагине-владельце это сам модуль. В любом другом плагине сборка ставит на
его место прокси: те же функции и типы, а каждый вызов выполняется у
владельца. Поэтому у меню пункты от всех плагинов, у игрока одно открытое
меню, а папка конфигов одна на весь сервер - кто бы её ни задал. Код плагина
и то, что видит его редактор, в обоих случаях одинаковы.

Модуль, для которого плагина с таким именем нет (`~/modules/http`),
компилируется в каждый импортирующий плагин, как раньше.

## Чей модуль

Плагина, чей файл называется как модуль: `as/<имя>.ts` владеет
`as/modules/<имя>.ts`. На сервере, где плагин собирается из папки плагинов,
считается и `<имя>.aot` в ней. Владелец должен быть в `plugins.ini`; вызов,
пока он не запущен, пишет строку в лог (`~/modules/menu-core: no plugin runs
it - is menu-core.aot in plugins.ini?`) и ничего не возвращает - `false`,
`0`, `""`, `null`.

Владелец регистрирует модуль, пока выполняется его верхний уровень, поэтому
плагин, стоящий в `plugins.ini` раньше владельца, может звать модуль из
`server.addEventListener("init", ...)` и позже, но не со своего верхнего
уровня.

## Что передаётся

| В модуле | Между плагинами |
| --- | --- |
| `number`, `boolean`, `string`, юнион строк | как есть |
| `T[]`, `T \| null` | как есть |
| `Player` | по id |
| объект, который модуль отдаёт и принимает обратно (`Menu`, `Config`, `Section`) | объект владельца: поля читаются и пишутся у него |
| любой другой объект - интерфейс, класс из полей (`MenuShowOptions`, `ListRow`, `SectionEntry`) | копия |
| объект с методами (`MenuEvent`) | копия, и после вызова его поля возвращаются: `event.preventDefault()` работает |
| функция (`ConditionTest`, `onSelect`, источник списка) | остаётся там, где написана; другая сторона вызывает её обратно |

«Отдаёт и принимает обратно» - одна экспортированная функция его
возвращает, другая принимает (`create()` возвращает `Menu`,
`addItem(menu, ...)` его принимает). Такой объект - один и тот же во всех
плагинах: `find("X")` дважды - один и тот же `Menu`, а `menu.title = "..."`
меняет меню владельца.

Функция, переданная через границу, остаётся одной функцией: одна и та же,
зарегистрированная дважды, приходит той же самой, и модуль может её
сравнить.

## Что не передаётся - и об этом сказано

Сборка останавливается с именем модуля, функции и параметра, если
экспортированная функция модуля, у которого есть владелец:

- принимает или возвращает тип, который не передаётся, - `Map`, `Set`,
  обобщённый класс, класс стандартной библиотеки, тип, который модуль не
  экспортирует;
- имеет значение по умолчанию, которое другой плагин не вычислит, -
  `index: number = base` (литерал, `{}`, `[]`, `null` - можно);
- обобщённая, async или с rest-параметром;
- это экспортированная переменная (`export let count`): экспортируйте
  функцию, которая её читает или задаёт;
- отдаёт и принимает обратно класс с методами.

```
~/modules/bad: export function remember - parameter "counts": Map from the standard library cannot cross - pass its contents as an array or a record
```

## Ограничения

- Поле общего объекта, которое само массив или объект, читается копией:
  `menu.items.push(item)` меняет копию. Присвоить поле (`menu.items =
  items`) или вызвать функцию модуля (`addItem`) - меняет объект владельца.
- Каждый вызов копирует аргументы в обе стороны и идёт через модуль Xen:
  намного дороже вызова внутри одного плагина. Прочитать файл по секциям при
  старте - нормально; вызов на каждого игрока каждый кадр лучше не делать.
- Владелец и вызывающие его плагины собираются из одного исходника модуля:
  после его правки соберите их все (`bun run plugins` и `bun run dev` так и
  делают). Плагин, собранный с другой версией, вместо вызова получает строку
  в логе.

## Под капотом

- `scripts/shared-modules.ts` компилирует модуль отдельно, через asc, до
  плагина (asc не реентерабелен): экспортированные функции собираются как
  экспорты, так что известны и выведенные компилятором типы результатов, и
  поля всех типов. По ним пишется прокси, который компиляция плагина читает
  вместо файла модуля, а для владельца - диспетчер рядом с ним
  (`__xen_serve.ts`), который выполняет каждый вызов на настоящем модуле и
  регистрирует его под именем модуля. Хэш того, что передаётся, есть в
  обоих, и модуль их сравнивает.
- `as/remote.ts`: байтовые буферы, таблица функций плагина, которые другие
  вызывают обратно, таблица объектов, которые владелец отдал, и экспорт,
  который вызывает модуль, - `__xen_rpc`. Полученная функция - заместитель с
  той же сигнатурой, в `_env` которого записано, куда звонить, - механизм
  промисов (`__co_bindEnv`), который компилятор поддерживает на каждом
  косвенном вызове, когда сборка об этом просит.
- `runtime/src/module.cpp`: `xen_serve`, `xen_owner`, `xen_rpc` и три,
  которые переносят байты (`xen_rpc_take`, `xen_rpc_reply`,
  `xen_rpc_result`). Вызов выполняется в плагине-адресате так же, как
  обработчик события; вызов внутри вызова - условие, которое спрашивают,
  пока рисуется меню, - такой же вызов.
