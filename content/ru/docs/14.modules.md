Модуль — код на TypeScript, который другие плагины импортируют по имени
пакета — `import * as greeter from "@you/greeter"`. То, что он экспортирует, —
функции и типы — и есть его API. Модуль говорит о себе через `defineModule`,
проект перечисляет его в `amxts.config.ts`, а на сервере работает один его
экземпляр. menu-core и universal-config — модули.

## Устройство

Модуль — пакет npm:

```
greeter/
├── package.json
├── tsconfig.json       { "extends": "@amxts/core/as/tsconfig.json" }
├── README.md
├── LICENSE
├── src/
│   ├── index.ts        модуль: defineModule и API
│   ├── types.ts        его публичные типы (необязательно)
│   └── natives.ts      его нативы для Pawn-плагинов (необязательно)
├── include/
│   └── greeter.inc     Pawn-include этих нативов
└── test/
    └── greeter.test.ts
```

`package.json` указывает на них в поле `amxts`:

```json
{
  "name": "@you/greeter",
  "version": "1.0.0",
  "type": "module",
  "exports": { ".": "./src/index.ts" },
  "types": "./src/index.ts",
  "amxts": {
    "module": "src/index.ts",
    "natives": "src/natives.ts",
    "include": "include/greeter.inc"
  },
  "files": ["src", "include"]
}
```

- `module` — файл, который импортируют плагины. Обязателен.
- `natives` — плагин модуля с нативами для Pawn-плагинов
  ([нативы](/ru/docs/natives)). Без него сборка делает плагин, который только
  запускает модуль.
- `include` — Pawn-include этих нативов; он идёт в пакете для
  Pawn-плагинов. Сборка пишет его по нативам, если это не контракт.
- `contract` — `true`, когда include — оригинальный, от Pawn-плагина, и
  меняться не должен: сборка сверяет с ним нативы, а не пишет его (см.
  [три вида модуля](#три-вида-модуля)).

Так или иначе плагин модуля — его единственный экземпляр на сервере: любой
другой плагин, который импортирует модуль, вызывает этот экземпляр, с теми же
функциями и типами ([общие модули](/ru/docs/shared-modules)).

## Модуль

```ts twoslash
// src/index.ts
import { Player, print } from "@amxts/core";

export interface GreeterOptions {
	/** Чем приветствуют игрока. */
	greeting: string;
	/** Здороваться раз за карту. */
	once: boolean;
}

export default defineModule<GreeterOptions>({
	meta: { name: "greeter", configKey: "greeter" },
	defaults: { greeting: "Hello", once: true },
	setup(options) {
		greeting = options.greeting;
		once = options.once;
	},
});

declare module "@amxts/core" {
	interface ModuleOptions {
		greeter?: Partial<GreeterOptions>;
	}
}

let greeting = "";
let once = true;
const greeted: string[] = [];

/** Здоровается с игроком — раз за карту, если проект не решил иначе. */
export function greet(player: Player) {
	if (once && greeted.includes(player.name)) return;

	greeted.push(player.name);
	print(player, `${greeting}, ${player.name}!`);
}
```

Пишется как любой код плагина: тот же фасад, те же правила. `@amxts/core` —
это фасад, `~/facade` — тот же файл. Публичные типы могут жить в
`src/types.ts` и реэкспортироваться через `export * from "./types"`; блок
`declare module "@amxts/core"` можно положить туда же. Состояние модуля — его собственное;
другие плагины меняют его экспортированными функциями, а не
экспортированными переменными.

## defineModule

`defineModule` глобальная, как `defineNuxtConfig` в Nuxt: импорт не нужен.
Что она берёт:

| поле | что |
| --- | --- |
| `meta.name` | имя пакета без scope: `menu-core` у `@amxts/menu-core` |
| `meta.configKey` | ключ, под которым настройки модуля пишутся в `amxts.config.ts` |
| `requires` | пакеты-модули, которыми модуль пользуется: они тоже должны быть в проекте и загружаются раньше |
| `defaults` | значение каждой настройки, когда проект её не задал |
| `setup(options)` | выполняется один раз, в плагине модуля, когда сервер его загружает, — раньше `init` любого плагина |

`setup` получает значения по умолчанию, поверх которых — настройки проекта:
настройка-объект сливается по ключам, остальное заменяется. Здесь модуль их
применяет — и здесь же слушает сервер (`server.addEventListener`), если ему
нужно.

::warning
**Только литералы**<br>
`meta`, `requires` и `defaults` сборка читает из исходника, не выполняя его.
Они пишутся литералами — строки, числа, булевы, массивы и объекты из них, — а
тип настроек называется: `defineModule<GreeterOptions>(...)`.
::

Блок `declare module "@amxts/core"` добавляет ключ модуля в `ModuleOptions`,
и редактор проверяет `amxts.config.ts` проекта: `greeter: { greting: "Hi" }`
там красное, с «Did you mean greeting?».

## Три вида модуля

### Без нативов

В поле `amxts` — только `module`. Плагин модуля сборка делает сама;
TypeScript-плагины модулем пользуются, Pawn-плагины вызвать его не могут.

### С нативами

```ts twoslash
// src/natives.ts
import { Player, plugin } from "@amxts/core";
import * as greeter from "./index";

plugin({ name: "Greeter", version: "1.0.0", author: "you", description: "Greets players" });

/** Greets a player - for Pawn plugins. */
export function greeter_greet(player: Player) {
	greeter.greet(player);
}
```

Каждая `export function` — натив для Pawn-плагинов ([нативы](/ru/docs/natives)).
`npx amxts build` в папке модуля собирает его и пишет `include/greeter.inc`
по нативам — сигнатуры из их типов, комментарии из JSDoc:

```pawn
/** Greets a player - for Pawn plugins. */
native greeter_greet(id);
```

Include коммитится вместе с изменением: по нему компилируются Pawn-плагины.

### Порт Pawn-плагина: контракт

Модуль, который заменяет Pawn-плагин, — как universal-config заменяет
universal_config.amxx, — сохраняет include этого плагина, чтобы
скомпилированные `.amxx` загружались с ним без изменений. Об этом говорит
`package.json`:

```json
"amxts": {
  "module": "src/index.ts",
  "natives": "src/natives.ts",
  "include": "include/universal_config.inc",
  "contract": true
}
```

Тогда сборка include не пишет. Сигнатуру каждого натива она берёт из него —
`Float:`, теги, ссылки `&`, буфер `out[], len` — и останавливается, если
экспорт с ним не сходится:

```
universal-config.ts: export function cfg_load_file - parameter "extra": the include declares no argument for it
universal-config.ts: universal_config.inc declares cfg_load_file, and the plugin does not export it
```

## Перед публикацией

```sh
npx amxts check
```

в папке модуля проверяет, что пакет готов, — для CI перед `npm publish`:

- поле `amxts` указывает на файлы, которые есть;
- в файле модуля есть `defineModule` с его `meta.name`;
- есть `README.md` и `LICENSE`;
- нативы компилируются, а include — ровно то, что по ним пишет
  `npx amxts build`, не устаревший после правки `natives.ts`; при
  `"contract": true` — что нативы сходятся с include.

```
ok   "amxts" points at src/index.ts, src/natives.ts, include/greeter.inc
ok   defineModule: greeter, options under "greeter"
ok   include/greeter.inc is up to date with 1 natives
```

## Модуль поверх другого модуля AMX Mod X

Модуль может оборачивать сторонний модуль или плагин AMX Mod X —
`~/modules/http` оборачивает easy_http. При первом вызове он проверяет, что
нужное загружено, и пишет в лог одну понятную строку вместо ошибки о
пропавшем нативе. Что ему нужно, пишется в README — чтобы владелец сервера
знал, что поставить.

## Модуль внутри проекта

Код, общий для плагинов проекта, — модуль без пакета: файл
`modules/<name>.ts` в папке плагинов, импорт — `~/modules/<name>`. Он
собирается в каждый плагин, который его импортирует, — у каждого своя копия
со своим состоянием. Папка `modules/<name>/` рядом с `amxts.config.ts` с
таким же `package.json`, как выше, — тоже пакет-модуль: он находится по
имени, как установленный.

## Как поделиться

[Каталог модулей](/ru/modules) показывает пакеты из npm. Чтобы модуль туда
попал, в его `package.json` есть ключевое слово `amxts-module` и ещё одно —
для категории:

```json
{
  "keywords": ["amxts-module", "amxts-menus"]
}
```

| ключевое слово | категория |
| --- | --- |
| `amxts-menus` | меню |
| `amxts-config` | конфигурация |
| `amxts-network` | сеть |

Потом `npm publish`. Каталог перечитывает npm в течение часа; на странице
модуля показывается его README.
