Статус: работает под `bun test` 2026-09-23 - `tests/showcase.test.ts`,
`tests/timers.test.ts`, `tests/game-events.test.ts` и
`tests/fake-server.test.ts` гоняют на нём `as/showcase.ts` и небольшой
тестовый плагин. Поддельный сервер - заменитель: его ответы сверены с модулем
и AMX Mod X по их коду, а не на игровом сервере.

Тест загружает настоящий код плагина - собранный тем же AssemblyScript, с тем
же фасадом и теми же сгенерированными нативами, что и `bun run plugins`, - в
поддельный сервер на TypeScript и управляет им так, как это делали бы игроки
и игра:

```ts
import { expect, setDefaultTimeout, test } from "bun:test";
import { loadPlugin } from "../src/testing";

setDefaultTimeout(60_000);   // первый тест собирает плагин

test("/tour показывает игроку его здоровье", async () => {
	const server = await loadPlugin("as/showcase.ts");
	const player = server.join("Alice", { team: "CT", health: 100 });

	player.say("/tour");
	expect(player.chat).toContain("Alice: 100 HP");

	server.advance(5000);                       // срабатывают таймеры
	expect(player.get("gravity")).toBe(1);
});
```

`bun test tests` запускает это вместе со всем остальным. Плагин собирается
один раз за прогон, а каждый `loadPlugin` получает свой экземпляр, так что
тесты не делят состояние.

## Как это устроено

Wasm плагина импортирует из `env` функции двух видов, и поддельный сервер
отвечает на оба:

- **мост**, который объявляет фасад (`on`, `clcmd`, `task`, `slot`, `hook`,
  `call`, `arg_text`, `say_text` ...), - сделан так же, как в
  `runtime/src/module.cpp`: слоты обратного вызова, реестр событий и Fire с его
  исходом;
- **нативы** из `as/natives.ts`, принимающие ячейки Pawn, - в
  `src/testing/natives.ts`, поверх поддельных игроков и сущностей.

Один флаг отличается от серверной сборки: тестовая экспортирует верхний
уровень плагина как `_start`, потому что импорт на JavaScript не может читать
память плагина, пока тот ещё создаётся. Он вызывается сразу после, так что
порядок серверный: верхний уровень, затем `init`, затем `cfg`.

**Натив, на который подделка не отвечает, останавливает тест** с его именем:
`the fake server does not implement "get_user_time" yet - add it to
src/testing/natives.ts`. Подделка покрывает то, что нужно тестам, и растёт
так же - натив там занимает несколько строк.

## Сервер

```ts
const server = await loadPlugin("as/showcase.ts", {
	map: "de_inferno",                          // "de_dust2"
	maxPlayers: 20,                             // 32
	modules: ["cstrike", "fun"],                // что находит hasModule(); по умолчанию все
	cvars: { mp_freezetime: "5" },              // до загрузки плагина
});
```

Несколько плагинов в одном сервере - массивом:
`loadPlugin(["as/a.ts", "as/b.ts"])`; они слышат форварды друг друга.

| | |
| --- | --- |
| `server.join(name, options)` | игрок заходит: `client_connect`, `client_authorized`, `client_putinserver` |
| `server.advance(ms)` | двигает часы и по порядку запускает все таймеры, чей срок подошёл |
| `server.fire(name, ...args)` | поднимает форвард - `"plugin_cfg"`, `"client_command"`, `"nhnse_on_round_end"` - для обработчиков и для `Forward.subscribe()` |
| `server.fireHook(event, args, { result })` | прогоняет хукчейн; см. ниже |
| `server.native(name, ...args)` | вызывает натив плагина из `export function` так, как Pawn, — текст, `Float`, массивы, буфер для результата — и отдаёт то, что прочитал бы Pawn: текст, массив, число |
| `server.xenNative(name, ...args)` | вызывает собственный натив модуля для Pawn - семейство `xen_*_player_data*` - так, как Pawn-плагин; `server.playerData` - само хранилище |
| `server.nativeWithRoom(name, room, args)` | то же с буфером результата на `room` ячеек (`charsmax(out)` или `size` массива) |
| `server.callNative(name, ...args)` | вызывает натив, который плагин экспортировал через `nativeFn` |
| `server.writeFile(path, text)` / `server.file(path)` | папка игры, которую видят `fs` и файловые нативы, — в памяти |
| `server.setCvar(name, value)` / `server.cvar(name)` | квар, как его ставит консоль; слушатели изменения его слышат |
| `server.vault(name)` | nVault хранилища `Storage` как `Map` - заполните его до того, как плагин прочитает |
| `server.log` | что написали `console.log` и `server_print`, строка за строкой |
| `server.commands` | что выполнил `server.command()` |
| `server.forwards` | отправленные форварды, `{ name, args }` |
| `server.players`, `server.player(id)` | кто подключён |
| `server.time` | миллисекунды с начала карты |
| `server.roundEnds` | раунды, которые плагин закончил (`game.endRound`, `rg_round_end`): `{ status, event, delay, message, sound, trigger }` |
| `server.sounds` | сыгранные звуки: `rh_emit_sound2` от сущности, `rg_send_audio` игроку - `{ entity, sample }` |
| `server.userMessages` | отправленные пользовательские сообщения (`player.screen.*`, `message_begin` ... `message_end`) по порядку: `{ name, player, args }` - `args` это значения `write_*`, строка - текстом: `{ name: "ScreenFade", player: 1, args: [2048, 0, 0, 200, 0, 0, 100] }` |
| `server.semiclipMasks` | маска resemiclip каждого игрока |
| `server.bartimes`, `server.rules`, `server.precached` | полоска прогресса у каждого игрока; члены game rules, которые записал плагин; что прекешировано |
| `server.touch(a, b)` | один игрок касается другого: все обработчики `register_touch` |
| `server.answerCvar(player, cvar, value)` | ответ клиента на `query_client_cvar` |

Плагин, который ждёт - async-функция, `sleep`, промис, - работает здесь как
на сервере: он собирается с экспортами планировщика корутин и Asyncify, а
`src/testing/coroutines.ts` играет роль планировщика модуля, так что
`sleep(1000)` продолжается, когда `server.advance()` его проходит.

## Игроки

```ts
const alice = server.join("Alice", {
	team: "CT",                                  // "CT"
	health: 100, armor: 0, alive: true,
	bot: false,
	authid: "STEAM_0:0:42",                      // STEAM_0:0:<id>, у бота BOT
	flags: "abcu",                               // буквы users.ini; "z"
	origin: [0, 0, 0],
	weapons: ["weapon_knife", "weapon_usp"],     // первое - в руках; нож
});

alice.say("/tour");                     // true, если плагин его забрал
alice.sayTeam("rush b");
alice.command("amx_slap \"Bob\" 5");    // консольная команда, разбитая как это делает движок
alice.disconnect({ dropped: true, reason: "Kicked" });
```

Что ему показали, строка за строкой, без байтов цвета: `alice.chat`,
`alice.center`, `alice.console`, `alice.hud`; все строки по порядку - в
`alice.messages`, а `alice.clearMessages()` начинает заново. Строка чата,
которую не забрал ни один плагин, попадает в чат всем как `Alice: text`.

Его состояние: `health`, `armor`, `frags`, `deaths`, `team`, `alive`,
`origin`, `muted`, `items` и `activeItem` (оружие с полем `kind`), `ammo` (по
имени оружия), `commands` (что `client_cmd` выполнил в его консоли).

## Сущности

Игрок и оружие - сущности, как и всё, что создаёт `create_entity`, -
`server.createEntity("info_target")`. Любое поле entvar или member читается и
пишется по имени, с префиксом или без; дробное - число, вектор - массив из трёх:

```ts
alice.get("gravity");          // 0.5
alice.set("renderfx", 19);
alice.get("rendercolor");      // [0, 160, 255]
alice.get("m_iHideHUD");       // 32
```

## Хукчейны

`fireHook` прогоняет цепочку так, как её прогнала бы игра: pre-слушатели,
собственная функция игры, если её никто не остановил, затем post-слушатели.

```ts
const hit = server.fireHook("takeDamage", [victim.id, 0, attacker.id, 30.0, DMG_BULLET], { result: 1 });
hit.prevented;   // pre-слушатель вызвал preventDefault() или ответил
hit.result;      // ответ цепочки после всех слушателей
hit.args;        // аргументы, какими их оставили слушатели (event.damage = ...)

server.fireHook("flPlayerFallDamage", [player.id], { result: 40 }).result;   // 20 с post-слушателем, делящим пополам
```

Событие называется так же, как в `game.addEventListener`, или коротким именем
reapi (`"take_damage"`). Аргументы - собственные аргументы цепочки по порядку;
дробный пишется числом. `result` - что отвечает функция игры, когда она
выполняется, - то, что post-слушатель читает как `event.result`. Ответ
возвращается в типе цепочки: число, boolean или текст.

## Таймеры

`setTimeout` и `setInterval` идут только по поддельным часам:
`server.advance(45_000)` запускает 45-секундный интервал один раз,
`advance(90_000)` - два, а `clearTimeout` до этого - ни разу.

## На настоящем сервере: `bun run test:server`

Статус: работает 2026-09-24 - 11 наборов, 110 проверок, на ReHLDS + ReGameDLL +
AMX Mod X 1.10 + reapi + YaPB.

Чего поддельный сервер сказать не может - перепривязывает ли движок
сущность, как загрузчик принимает сборку под i386, что доходит до консоли, -
проверяется на настоящем HLDS, без людей в игре:

```sh
bun run test:server              # сборка, все наборы, остановка, уборка
bun run test:server --keep       # оставить тестовый сервер работать, чтобы посмотреть
bun run test:server --stop       # остановить оставленный --keep и убрать его папки
bun run test:server --port 27020 # другой порт (XEN_TEST_PORT; по умолчанию 27016)
```

Он собирает наборы, запускает второй hlds из той установки, на которую
указывает `XEN_SERVER`, шлёт каждому набору его команду по rcon, читает, что
напечатал сервер, и выходит с 0 или 1:

```
built 9 plugins and 1 Pawn suite(s) (42.8s)
test server: hlds pid 23292 on 127.0.0.1:27016, c21_kitty

ok   async              5 ok
ok   universal-config   16 ok
FAIL player             4 ok, 1 failed
       [player] FAIL аргументы команды: got @07 420, expected раз два
ok   time               6 ok

FAIL: 61 checks passed in 8 suites, 1 failures
the console and any crash dump: dist-wasm/test-server/last-run
```

Падение сервера, незагрузившийся плагин или строка вроде `failed to load`,
`resolve symbol` или `Exception` в консоли - тоже провал, со строками вокруг.
После провала консоль и дамп падения остаются в
`dist-wasm/test-server/last-run`.

### Работающий сервер не трогается

Тестовый сервер может стартовать, пока на сервере установки кто-то играет:

- другой порт (27016), только 127.0.0.1, случайный пароль rcon и свой
  `server.cfg` (`+servercfgfile`);
- `+localinfo amxx_cfg` даёт AMX Mod X тестовый `core.ini`, который уводит
  список плагинов, плагины, модули, конфиги и логи в
  `cstrike/addons/xen/test`. Одной командной строки мало: AMX Mod X читает
  `core.ini` после неё и перетирает. Модули - копии, и `xen_amxx.dll` среди
  них - из `runtime/build`, проверяемая сборка, а работающий сервер держит
  свою;
- `+localinfo xen_plugins addons/xen/test/plugins.ini` даёт модулю Xen свой
  список плагинов. Плагины ищутся в `plugins/` рядом со списком, и
  `addons/xen` для такого сервера модуль не раскладывает;
- лог консоли (`-condebug`) hlds пишет в рабочую папку - туда же, куда пишет
  работающий сервер. Поэтому тестовый сервер работает в папке `xen-test`
  рядом с `hlds.exe`, из junction-ссылок на `cstrike`, `valve` и `platform`:
  hlds находит игру там, где ждёт, а лог у теста свой;
- останавливается он по номеру процесса, никогда по имени, и обе папки в
  конце удаляются.

До запуска раннер отказывается от порта, который уже занят каким-нибудь hlds.
Когда сервер поднялся, раннер проверяет, что AMX Mod X крутит только плагины
теста и что модуль Xen взял тестовый список; если нет - на этом
останавливается.

### Как написать набор

Набор - плагин в `tests/server/`: `.ts`, собранный как плагин из `as/` (с
`~/`), или `.sma`, собранный `amxmodx/base/amxxpc.exe` с include'ами, которые
экспортируют `.ts`-наборы. В список плагинов сервера он не попадает никогда.
Он регистрирует команду сервера `xen_test_<имя>` и пишет проверки через
`Checks` из `~/lib/check`, созданный без игрока:

```ts
import { Cvar, server } from "~/facade";
import { Checks } from "~/lib/check";

const answer = new Cvar("xen_test_answer", "42");   // нарочно на верхнем уровне

server.addServerCommand("xen_test_cvar", (args) => {
	const check = new Checks("cvar");
	check.expect(answer.value, "значение по умолчанию").toBe("42");
	check.done();                                    // [cvar] N ok, M failed
});
```

- Метка - хвост команды, `_` пишется как `-`: `xen_test_universal_config`
  пишет в лог `[universal-config]`. Pawn-набор печатает такие же строки сам,
  через `server_print`.
- Раннер ждёт `[<имя>] N ok, M failed` 20 секунд, поэтому async-набор зовёт
  `check.done()`, когда закончил, а не когда вернулась команда.
- Строка `// @log <текст>` в наборе - текст, который консоль должна показать,
  пока он работает. Он ищется как написан - `// @log Привет, мир`
  проваливается, если кириллица пришла вопросами, - а строка с ошибкой,
  которую набор вызывает нарочно (ловушка в корутине), ошибкой не считается.
- Набору, которому нужен игрок, достаётся бот: раннер следит, чтобы он был на
  сервере (`yb add`), а `amxclient_cmd(bot.id, "say", "/cmd")` пишет за него
  команду в чат.
- Плагин, который нужен набору кроме него самого (`as/universal-config.ts`),
  перечислен в `EXTRA_PLUGINS` в `scripts/test-server.ts`; файл, который
  набор читает, кладётся в `tests/server/fixtures/` (копируется в конфиги
  тестового сервера); аргумент от раннера - в `SUITE_ARGS`.

Наборы: `cvar` (`Cvar` на верхнем уровне - `create_cvar` во время
`plugin_natives` ронял сервер), `entity` (`entity.origin`, потом
`Entity.findAll({ near, radius })` - перепривязка в движке), `time`
(`Date.now()`, `performance.now()`, `Math.random()` - `_alldiv` под i386),
`async` (порядок sleep, отмена, ловушка роняет одну корутину), `utf8`
(кириллица в консоли и через натив), `player` (чат-команда бота), `natives`
(Pawn-плагин зовёт нативы TypeScript-плагина: строки, `Float`, массивы,
буферы результата), `universal-config` (его нативы на
`fixtures/xen-test.ini`), `menu-core` (Pawn-набор: меню с плейсхолдером
Pawn-плагина и TS-плагина, строка источника списка и ключи перевода для бота
с `lang ru`, прочитанные через `mc_get_menu_text`; TS-плейсхолдер отдаёт
`menu-ts.ts`), `menu-lang` (`LookupLangKey` на языке бота и на языке
сервера) и `nhnse` (Pawn-набор, собранный против сгенерированного
`nhnse_core.inc`, как модули nhnse: квары из core.ini, ответы нативов так,
как их зовут модули, - буферы, `&ref`, `%L`, - `chooseteam` открывает боту
главное меню, перезапуск раунда даёт `nhnse_on_round_start`).
universal-config, menu-core и nhnse-core загружаются в каждом прогоне
(`EXTRA_PLUGINS`), с `fixtures/nhnse/core.ini` и `menu.ini`; папка конфигов
одна на сервер, поэтому набор, читающий свои файлы, выставляет её сам
(`cfg_set_base_dir("")`). Pawn-набор видит и `includes/` репозитория
(reapi, `nhnse_const.inc`).

Нужны `XEN_SERVER` в `.env`, собранный модуль (`runtime/build`), host-плагин
(`runtime/host/xen_host.amxx`) и YaPB на сервере для бота.
