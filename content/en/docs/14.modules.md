A module is TypeScript code other plugins import: a file `modules/<name>.ts`
in the plugins folder, imported as `~/modules/<name>`. What it exports — its
functions and types — is its API. menu-core, universal-config and http are
modules.

## Layout

```
addons/amxts/plugins/
├── modules/
│   └── greeter.ts      the module
└── greeter.ts          its plugin: one instance for the server
```

A module on its own is compiled into every plugin that imports it: each one
gets its own copy, with its own state. Give it a plugin of the same name and it
has one instance for the whole server — see [shared modules](/docs/shared-modules).
That plugin is also where a module's natives for Pawn plugins live
([natives](/docs/natives)).

## The module

```ts twoslash
// modules/greeter.ts
import { Player, print } from "~/facade";

const greeted: string[] = [];

/** Greets a player once per map. */
export function greet(player: Player) {
	if (greeted.includes(player.name)) return;

	greeted.push(player.name);
	print(player, `Hello, ${player.name}!`);
}

/** How many players were greeted. */
export function count() {
	return greeted.length;
}
```

Write it as any plugin code: the same facade, the same rules. State the module
keeps is private to it; other plugins change it through exported functions,
not exported variables.

## Its plugin

```ts twoslash
// greeter.ts
import { plugin } from "~/facade";
import "~/modules/greeter";

plugin({ name: "Greeter", version: "1.0.0", author: "you", description: "Greets players" });
```

Put it in `plugins.ini` before the plugins that use the module.

## Using it

```ts twoslash
declare const player: import("~/facade").Player;
// ---cut---
import { server } from "~/facade";
import * as greeter from "~/modules/greeter";

server.addEventListener("putinserver", event => greeter.greet(event.player));
```

Every plugin writes the same import. With the module's plugin running, they
all share one list of greeted players.

## A module over another AMX Mod X module

A module can wrap a third-party AMX Mod X module or plugin — `~/modules/http`
wraps easy_http. On first use it checks that what it needs is loaded, and
writes one clear line to the log instead of failing on a missing native. Say
what it needs in its README, so a server owner knows what to install.

## Sharing it

::warning
**Not a package yet**<br>
Installing a module with a package manager is being built. Until then a module
is shared as files: copy `modules/<name>.ts` and its plugin into the plugins
folder.
::

The [modules catalog](/modules) lists packages from npm. For a module to show
up there, publish it with a `package.json` that has the keyword `amxts-module`,
and one more keyword for its category:

```json
{
  "name": "amxts-module-greeter",
  "version": "1.0.0",
  "description": "Greets players once per map",
  "keywords": ["amxts-module"],
  "repository": "https://github.com/you/amxts-module-greeter",
  "files": ["modules/greeter.ts", "greeter.ts"]
}
```

| keyword | category |
| --- | --- |
| `amxts-menus` | menus |
| `amxts-config` | configuration |
| `amxts-network` | network |

Then `npm publish`. The catalog reads npm again within an hour; the module's
page shows its README.
