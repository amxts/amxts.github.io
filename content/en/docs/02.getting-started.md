amxts runs Counter-Strike 1.6 plugins written in TypeScript inside AMX Mod X,
next to your Pawn plugins. A plugin is an ordinary `.ts` file: players are
objects, events have types, and the editor knows every field the game has.
This page shows a project, a first plugin, how to reload it while you work,
and what is different from the TypeScript you already know.

## A project

A project is a folder with its plugins, the modules it uses and one config
file, `amxts.config.ts`, as a Nuxt app has `nuxt.config.ts`:

```
my-server/
├── package.json
├── amxts.config.ts
├── tsconfig.json       { "extends": "./.amxts/tsconfig.json" }
└── plugins/
    └── hello.ts
```

::code-group{sync="pm"}

```sh [npm]
npm install -D @amxts/core @amxts/universal-config @amxts/menu-core
```

```sh [pnpm]
pnpm add -D @amxts/core @amxts/universal-config @amxts/menu-core
```

```sh [yarn]
yarn add -D @amxts/core @amxts/universal-config @amxts/menu-core
```

```sh [bun]
bun add -d @amxts/core @amxts/universal-config @amxts/menu-core
```

`defineConfig` is global — no import. `modules` lists the module packages the
project uses; each module's options go under its own key (`menus` is
menu-core's), and the editor checks them against the module. `pluginsDir`
(`"plugins"`) and `outDir` (`"dist"`) say where the plugins are and where the
build writes. See [creating a module](/docs/modules) for the other side.

```sh
npx amxts build            # the plugins and the modules' plugins into dist/, with plugins.ini
npx amxts build --deploy   # and copies them to the server
npx amxts dev              # builds, deploys, and again on every save
npx amxts typecheck        # checks the project as the editor does
```

The build writes `plugins.ini` itself: the modules first, each after the
modules it requires, then the project's plugins. It also writes
`.amxts/tsconfig.json`, which the project's `tsconfig.json` extends: that is
how the editor knows `~/facade`, the modules by their names and the options in
`amxts.config.ts` (`npx amxts prepare` writes it alone).

The editor's tooltips - on `print`, `Player`, events, fields, the modules'
functions - are in English, or in Russian with `AMXTS_DOCS_LANG=ru` in the
project's `.env`; `npx amxts prepare` (and every build) switches them.

::tip
**Bun**<br>
The build runs on [Bun](https://bun.sh) for now: `npx amxts` starts it with
Node, and it hands the work to Bun, so Bun has to be installed.
::

## Your first plugin

```ts twoslash
import { Player, plugin, print, server } from "~/facade";

plugin({ name: "Hello", version: "1.0.0", author: "you", description: "An example" });

server.addCommand("/hp", sayHp);
server.addEventListener("putinserver", (event) => {
	print(0, `${event.player.name} joined`);
});

function sayHp(player: Player) {
	print(player, `${player.name}, your HP: ${player.health}`);

	if (player.health < 50) player.health = 100;
}
```

Put the file in the project's `plugins/` and run `npx amxts build --deploy`.
A plugin also works without a project: a `.ts` file in `addons/amxts/plugins`,
with its name in `plugins.ini`, is compiled by the server on save and loaded
without a map change.

## Hot reload

```sh
npx amxts dev
```

`dev` builds every plugin and deploys it, then watches your plugins folder
and the modules the project uses. When you save a file, it rebuilds the plugins that import that file,
copies them to the server and reloads the running server over rcon:

```
rebuilt my-plugin (6.8s) -> deployed -> reloaded
  [amxts] reloading
```

A change to a shared file rebuilds every plugin that imports it. A compile
error shows as `file.ts:line:col - message` above the line it points at. The
server keeps the last good build.

- `AMXTS_SERVER` in `.env` says where the server is, as it does for `--deploy`.
- The reload goes through rcon to `127.0.0.1:27015` (set `AMXTS_PORT` to use
  another port). The password is read from `rcon_password` in the server's
  `cstrike/server.cfg`. Without a password the module still reloads a changed
  `.aot` by itself, but you do not see its reply.
- A **new** plugin is written into `plugins.ini`, but it loads only after a
  server restart. `dev` tells you when this happens.
- If the server is not running, the command only builds and deploys.
  It never starts or stops hlds.

## What's different about the language

A plugin is ordinary TypeScript, but AssemblyScript compiles it to
WebAssembly. The differences you will notice:

- `number` is JavaScript's number, whole or not: `7 / 2` is `3.5`, and
  `` `${hp}` `` prints `"100"`. Bitwise operators take it as int32, as in JS.
  A Pawn cell is an integer, but you never convert: natives and the facade do
  it on their own.
- A handler may use the variables around it — it is a closure, as in
  JavaScript: `setTimeout(() => print(player, "Welcome!"), 2000)` inside a
  listener, a counter an interval shares with the function that set it,
  `this` in an arrow written in a method.
- A string union (`"Money" | "Timer"`) works as in TypeScript: the editor
  suggests and checks it, the compiler sees `string`. An open one, where any
  other string goes too, is written as in TypeScript: `"normal" | "dm" |
  (string & {})` — the editor still suggests the literals. There are no
  other unions except `T | null` and `T | undefined`.
- `a ?? b` and `a ??= b` work as in TypeScript: the right side is taken only
  when the left is `null` or `undefined` (not `""` or `0`), and
  `ini.getValue(section, "KEY") ?? ""` is a `string`.
- Options are an interface with optional fields, as in TypeScript: a field
  left out of the object literal is `undefined`, and the function gives it
  its default with `??` or by destructuring:

  ```ts
  interface GreetOptions {
  	times?: number;
  	loud?: boolean;
  	onDone?: (player: Player) => void;
  }

  function greet(player: Player, { times = 1, loud = false }: GreetOptions = {}) { ... }

  function farewell(player: Player, options: GreetOptions = {}) {
  	if (options.times !== undefined) print(player, `${options.times} times`);
  	options.onDone?.(player);
  }

  greet(player, { loud: true });
  ```

  `=== undefined` narrows as in TypeScript, `options.onDone?.(player)` calls
  only when there is a function, `a?.b` and `a?.[i]` read through a missing
  object.
- `for...in` does not exist: an object's properties cannot be listed while
  the plugin runs. Walk an array with `for (const item of list)`, or keep the
  data in a `Map`: `for (const key of map.keys())`.
- A function goes where a longer function type is expected, as in
  TypeScript: `server.addCommand("/gel", gel)` with `function gel(player:
  Player)` gets the player and not the arguments - no `(player, args) =>
  gel(player)` needed.

::warning
**Reading a variable before its declaration**<br>
As in JavaScript, a `let` or `const` read before its declaration has run - by
a function declared below and called above it, or by a closure the variable's
own initializer calls - is an error: `x is not initialized`. There is no
exception to catch here: the server console shows the message with the file
and the line, the current call ends, and the plugin and the server go on.
::
