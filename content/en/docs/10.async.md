## async and await

It is JavaScript's `async`/`await`:

- An `async` function returns a `Promise` at once and runs up to its first
  `await`. What it returns is what the promise is fulfilled with:
  `async function count() { return 3; }` is a `Promise<number>`.
- A call without `await` does not wait: `countdown(player)` runs on its own,
  and the line after the call runs straight away.
- `await promise` gives the promise's value once there is one. The rest of
  the function runs later - on the frame the value came in - while the server
  gets on with everything else. Even an `await` of a promise that has settled
  already lets what is running finish first, as in JavaScript.
- `await` is allowed in `async` functions, arrows and methods only.

An async function can be a listener anywhere a listener goes:
`server.addEventListener`, `game.addEventListener`, `server.addCommand`,
`Forward.subscribe` and a Cvar's `"change"`. What it tells the game counts
only if it says it **before its first `await`**: a game listener's `return`
value, `event.preventDefault()`, a command being handled. Once it waits, the
game has moved on and gets no answer from it - the listener simply continues
later.

```ts
game.addEventListener("flPlayerFallDamage", async (event) => {
	if (safe) return 0;          // the chain's answer: no fall damage
	await sleep(100);
	return 0;                    // too late - the damage has been dealt
});
```

## Promise

The global `Promise`, as in JavaScript: `then`, `catch`, `finally`,
`Promise.resolve`, `Promise.reject`, `Promise.all`, `Promise.allSettled`,
`Promise.race` and `Promise.any`.

```ts
const [first, second] = await Promise.all([fetch(a), fetch(b)]);
const fastest = await Promise.race([fetch(a), fetch(b)]);

fetch(url)
	.then((response) => console.log(`${response.status}`))
	.catch((error) => console.error(error.message));
```

`new Promise((resolve, reject) => ...)` wraps an API that calls back. The
executor runs at once; since a function here cannot use the locals around it
(there are no closures), keep `resolve` at the top of the file and call it
from the callback:

```ts
let answered: ((value?: string) => void) | null = null;

function ask(player: Player) {
	return new Promise<string>((resolve) => {
		answered = resolve;
		showMenu(player);
	});
}

function onMenuChoice(choice: string) {
	const resolve = answered;
	if (resolve) resolve(choice);
}
```

- A `.then` callback returns a value. To follow one request with another,
  `await` them.

### Promise.all and allSettled: a tuple

Promises of different types, written out in the call, give a tuple, as in
TypeScript - each value with its own type:

```ts
const [response, _] = await Promise.all([fetch(url), sleep(1000)]);    // Response, void
const [count, name] = await Promise.all([countAsync(), nameAsync()]);  // number, string

const [page, rank] = await Promise.allSettled([fetch(a), rankAsync()]);
if (page.status == "fulfilled") print(player, page.value.text);
if (rank.status == "rejected") console.error(rank.reason.message);
```

- Promises of one type, or a list in a variable, give an array, as before:
  `(await Promise.all(list)).length`.
- A tuple is read by destructuring or by an index written as a number:
  `results[0]`. An index past its end is a compile error, as in TypeScript.
  `for...of`, `.map` and `.length` are for arrays.
- Up to 8 promises of different types in one call.
- `allSettled` is fulfilled once every promise has settled, either way. Each
  result has `status` - `"fulfilled"` with `value`, or `"rejected"` with
  `reason` (an `Error`). A rejection it has seen is not reported as unhandled.

### Promise.race and any: one value

`race` settles like the first promise to settle. `any` takes the first value
and passes rejections by; when every promise is rejected, it is rejected
with an `AggregateError` whose `errors` hold each reason.

```ts
const response = await Promise.race([fetch(url), sleep(3000)]);   // Response | null
if (!response) return;                                            // the sleep won
print(player, response.text);

const fastest = await Promise.any([fetch(mirrorA), fetch(mirrorB)]);
```

The value is of one type, so the promises need one:

- the same type - the value is of that type;
- a `Promise<void>` (a `sleep`, an async function that returns nothing)
  beside one type - the value is that type or `null`. The editor says
  `Response | void`, and `if (!response) return` reads the same in both;
- classes with a common base class - the value is of that class
  (`Promise.race([cat(), dog()])` is an `Animal`).

Anything else - a number and a string, say - is a compile error:
`Promise.race of 'number' and 'string': their values share no type. Await
them one by one, or give them a common base class.` TypeScript would make it
`number | string`, a union AssemblyScript has no way to hold.

## Errors

There is no `try`/`catch`: AssemblyScript has no exceptions. A rejection
travels the way an exception would:

- `.catch` gets it.
- `await` of a rejected promise ends the awaiting function there, and its own
  promise is rejected with the same error - up to whoever has a `.catch`.
- If nobody handles it, the console gets one line, as Node writes it:
  `Unhandled promise rejection: <message>`. A cancellation (an error named
  `AbortError` or `TimeoutError`) is expected and is not reported.

Reject with `new Error(message)`; `error.message` and `error.name` read back.

A crash inside an async function - an index out of range, a null - after an
`await` names the plugin in the console and drops that one function; the
plugin and the server run on.

## sleep

```ts
await sleep(1000);
await sleep(5000, { signal: AbortSignal.timeout(2000) });   // rejected after 2 s
```

A promise fulfilled after `ms` milliseconds. Underneath it is a server timer
(`set_task`), as fine-grained as a server frame.

## Cancelling: AbortController and AbortSignal

As in the browser:

```ts
const controller = new AbortController();
fetch(url, { signal: controller.signal }).catch((error) => console.log(error.name)); // "AbortError"
controller.abort();

controller.signal.aborted;          // true
controller.signal.reason;           // the Error it was aborted with
controller.signal.addEventListener("abort", (event) => console.log("aborted"));

await fetch(url, { signal: AbortSignal.timeout(3000) });   // "TimeoutError" after 3 s
```

- `fetch(url, { signal })` cancels the request (`ezhttp_cancel_request`) and
  rejects with the signal's reason - an Error named `AbortError` unless
  `abort()` was given another.
- `sleep(ms, { signal })` stops its timer and rejects the same way.
- `AbortSignal.timeout(ms)` aborts by itself, with an Error named
  `TimeoutError`; `AbortSignal.abort()` has aborted already;
  `AbortSignal.any([a, b])` aborts with whichever does first.
- Timers - `sleep` and `AbortSignal.timeout` - tick every 0.1 s, as
  AMX Mod X's do: `timeout(1)` fires after about 100 ms.

### When the player leaves

`player.signal` aborts when that player disconnects (the stock
`client_disconnected` forward), and the next player in the slot gets a fresh
one:

```ts
const stats = await fetch(url, { signal: player.signal });
```

An async **command handler** or **player event** listener (`putinserver`,
`connect`, `authorized` and the rest whose event has a `player`) needs not
even that: it runs under that player's signal. Every `await` in it - a fetch,
a sleep, any promise - ends quietly when the player leaves, with no line in
the console and nothing to clean up:

```ts
server.addCommand("/rank", async (player) => {
	const rank = await fetch(`https://example.com/rank/${player.authid}`);  // cancelled if he leaves
	print(player, rank.text);                                                // never runs then
});
```

A `signal` passed explicitly works alongside: whichever aborts first. Async
functions called from such a handler run under the same signal. Game
(hookchain) listeners and the leaving events themselves do not get one.

## The world after an await

A function that awaited resumes in a later frame, and much may have changed:
the round ended, the player died - or left. Under a player's signal a
departure ends the function for you; elsewhere check `player.isConnected`
after an `await` before you use the player again.

## Limits

- `for await` and async generators are not supported.
- Tuple types are not written in annotations: `const pair: [number, string]`
  does not compile. A tuple comes from `Promise.all`/`allSettled` and is
  destructured where it is awaited.
- `Promise.all([promise, 5])`: every element must be a promise; wrap a plain
  value in `Promise.resolve(5)`.
- `await` takes a `Promise`; awaiting a plain value is a compile error.
- An async arrow cannot use the locals around it (no closures); its own
  parameters are fine.
- A waiting async function keeps its state in 4 KB; one that needs more is
  dropped with a message naming the plugin.
- Cost: the code that can reach an `await` - async functions and what calls
  them directly - is instrumented by Binaryen's Asyncify, about 20% slower in
  a tight loop there. Nothing else changes, and a plugin with no async
  function is compiled exactly as before.
