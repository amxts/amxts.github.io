A test loads the plugin's real code - compiled by the same AssemblyScript,
against the same facade and generated natives as `bun run plugins` - into a
fake server written in TypeScript, and drives it the way players and the game
would:

```ts
import { expect, setDefaultTimeout, test } from "bun:test";
import { loadPlugin } from "../src/testing";

setDefaultTimeout(60_000);   // the first test compiles the plugin

test("/tour shows the player his health", async () => {
	const server = await loadPlugin("as/showcase.ts");
	const player = server.join("Alice", { team: "CT", health: 100 });

	player.say("/tour");
	expect(player.chat).toContain("Alice: 100 HP");

	server.advance(5000);                       // the timers run
	expect(player.get("gravity")).toBe(1);
});
```

`bun test tests` runs it with everything else. The plugin is compiled once per
run and every `loadPlugin` gets a fresh instance, so tests do not share state.

## How it works

A plugin's wasm imports two kinds of function from `env`, and the fake server
answers both:

- **the bridge** the facade declares (`on`, `clcmd`, `task`, `slot`, `hook`,
  `call`, `arg_text`, `say_text` ...) - implemented as `runtime/src/module.cpp`
  implements it: callback slots, the events registry, and Fire with its
  outcome;
- **the natives** from `as/natives.ts`, which take Pawn cells - implemented in
  `src/testing/natives.ts` against the fake players and entities.

One flag differs from the server build: the test build exports the plugin's
top level as `_start`, because a JavaScript import cannot read the plugin's
memory while it is still being instantiated. It runs straight after, so the
order is the server's: top level, then `init`, then `cfg`.

**A native the fake does not answer stops the test** with its name:
`the fake server does not implement "get_user_time" yet - add it to
src/testing/natives.ts`. The fake covers what the tests need and grows the
same way - a native is a few lines there.

## The server

```ts
const server = await loadPlugin("as/showcase.ts", {
	map: "de_inferno",                          // "de_dust2"
	maxPlayers: 20,                             // 32
	modules: ["cstrike", "fun"],                // what hasModule() finds; all of them
	cvars: { mp_freezetime: "5" },              // before the plugin loads
});
```

Several plugins go into one server as an array -
`loadPlugin(["as/a.ts", "as/b.ts"])` - and hear each other's forwards.

| | |
| --- | --- |
| `server.join(name, options)` | a player connects: `client_connect`, `client_authorized`, `client_putinserver` |
| `server.advance(ms)` | moves the clock and runs every timer that comes due, in order |
| `server.fire(name, ...args)` | raises a forward - `"plugin_cfg"`, `"client_command"`, `"nhnse_on_round_end"` - for handlers and `Forward.subscribe()` alike |
| `server.fireHook(event, args, { result })` | runs a hookchain; see below |
| `server.native(name, ...args)` | calls a plugin's `export function` native as Pawn would - text, `Float`, arrays, an out-buffer - and gives back what Pawn reads: the text, the array, the number |
| `server.xenNative(name, ...args)` | calls one of the module's own natives for Pawn - the `xen_*_player_data*` family - as a Pawn plugin would; `server.playerData` is the store itself |
| `server.nativeWithRoom(name, room, args)` | the same with an out-buffer of `room` cells (`charsmax(out)`, or an array's `size`) |
| `server.callNative(name, ...args)` | calls a native a plugin exported with `nativeFn` |
| `server.writeFile(path, text)` / `server.file(path)` | the game folder `fs` and the file natives see, in memory |
| `server.setCvar(name, value)` / `server.cvar(name)` | a cvar as the console sets it; change listeners hear it |
| `server.vault(name)` | a `Storage`'s nVault, as a `Map` - fill it before the plugin reads it |
| `server.log` | what `console.log` and `server_print` wrote, one line a line |
| `server.commands` | what `server.command()` ran |
| `server.forwards` | the forwards sent out, `{ name, args }` |
| `server.players`, `server.player(id)` | who is connected |
| `server.time` | milliseconds since the map started |
| `server.roundEnds` | the rounds a plugin ended (`game.endRound`, `rg_round_end`): `{ status, event, delay, message, sound, trigger }` |
| `server.sounds` | sounds played: `rh_emit_sound2` from an entity, `rg_send_audio` to a player - `{ entity, sample }` |
| `server.userMessages` | user messages sent (`player.screen.*`, `message_begin` ... `message_end`), in order: `{ name, player, args }` - `args` are the `write_*` values, a string as text: `{ name: "ScreenFade", player: 1, args: [2048, 0, 0, 200, 0, 0, 100] }` |
| `server.semiclipMasks` | resemiclip's mask per player |
| `server.bartimes`, `server.rules`, `server.precached` | the progress bar each player was shown; the game rules' members a plugin set; what was precached |
| `server.touch(a, b)` | one player touching another: every `register_touch` callback |
| `server.answerCvar(player, cvar, value)` | a client answering `query_client_cvar` |

A plugin that awaits - an async function, `sleep`, a promise - runs here as
on the server: it is compiled with the coroutine scheduler's exports and
Asyncify, and `src/testing/coroutines.ts` plays the module's scheduler, so a
`sleep(1000)` resumes when `server.advance()` passes it.

## Players

```ts
const alice = server.join("Alice", {
	team: "CT",                                  // "CT"
	health: 100, armor: 0, alive: true,
	bot: false,
	authid: "STEAM_0:0:42",                      // STEAM_0:0:<id>, BOT for a bot
	flags: "abcu",                               // users.ini letters; "z"
	origin: [0, 0, 0],
	weapons: ["weapon_knife", "weapon_usp"],     // the first in his hands; a knife
});

alice.say("/tour");                     // true if a plugin swallowed it
alice.sayTeam("rush b");
alice.command("amx_slap \"Bob\" 5");    // a console command, split as the engine splits it
alice.disconnect({ dropped: true, reason: "Kicked" });
```

What he was shown, one line a line, with the colour bytes taken out:
`alice.chat`, `alice.center`, `alice.console`, `alice.hud`; every line in
order is in `alice.messages`, and `alice.clearMessages()` starts again. A chat
line no plugin swallowed reaches everyone's chat as `Alice: text`.

His state: `health`, `armor`, `frags`, `deaths`, `team`, `alive`, `origin`,
`muted`, `items` and `activeItem` (weapons with a `kind`), `ammo` (by weapon
name), `commands` (what `client_cmd` ran in his console).

## Entities

A player and a weapon are entities, and so is anything `create_entity` makes -
`server.createEntity("info_target")`. Any entvar or member reads and writes by
its name, with or without the prefix; a float is a number and a vector an
array of three:

```ts
alice.get("gravity");          // 0.5
alice.set("renderfx", 19);
alice.get("rendercolor");      // [0, 160, 255]
alice.get("m_iHideHUD");       // 32
```

## Hookchains

`fireHook` runs a chain as the game would: the pre listeners, the game's own
function unless one of them stopped it, then the post listeners.

```ts
const hit = server.fireHook("takeDamage", [victim.id, 0, attacker.id, 30.0, DMG_BULLET], { result: 1 });
hit.prevented;   // a pre listener called preventDefault() or answered
hit.result;      // the chain's answer after every listener
hit.args;        // the arguments as listeners left them (event.damage = ...)

server.fireHook("flPlayerFallDamage", [player.id], { result: 40 }).result;   // 20 with a halving post listener
```

The event is named as `game.addEventListener` names it, or by reapi's short
name (`"take_damage"`). The arguments are the chain's own, in order; a float
argument is written as a number. `result` is what the game's function answers
when it runs - what a post listener reads as `event.result`. The answer comes
back typed by the chain: a number, a boolean or text.

## Timers

`setTimeout` and `setInterval` run on the fake clock and nothing else:
`server.advance(45_000)` runs a 45-second interval once, `advance(90_000)`
twice, and a `clearTimeout` before that means never.

## On a real server: `bun run test:server`

::tip
Status: works 2026-09-24 - 11 suites, 110 checks, on ReHLDS + ReGameDLL + AMX
Mod X 1.10 + reapi + YaPB.
::

What the fake server cannot tell - whether the engine relinks an entity, how
the loader takes the i386 build, what reaches the console - is checked on a
real HLDS, with nobody in the game:

```sh
bun run test:server              # build, run every suite, stop, clean up
bun run test:server --keep       # leave the test server running to look at it
bun run test:server --stop       # stop the one --keep left, remove its folders
bun run test:server --port 27020 # another port (XEN_TEST_PORT; 27016 by default)
```

It builds the suites, starts a second hlds from the install `XEN_SERVER`
points at, sends each suite its command over rcon, reads what the server
printed, and exits 0 or 1:

```
built 9 plugins and 1 Pawn suite(s) (42.8s)
test server: hlds pid 23292 on 127.0.0.1:27016, c21_kitty

ok   async              5 ok
ok   universal-config   16 ok
FAIL player             4 ok, 1 failed
       [player] FAIL аргументы команды: got @07 420, expected раз два
ok   time               6 ok

FAIL: 61 checks passed in 8 suites, 1 failures
the console and any crash dump: dist-wasm/test-server/last-run
```

A crash, a plugin that did not load, or a line such as `failed to load`,
`resolve symbol` or `Exception` in the console is a failure too, printed with
the lines around it. After a failed run the console and any crash dump are
kept in `dist-wasm/test-server/last-run`.

### The running server is left alone

The test server may start while someone plays on the install's own server:

- another port (27016), bound to 127.0.0.1, a random rcon password and a
  `server.cfg` of its own (`+servercfgfile`);
- `+localinfo amxx_cfg` gives AMX Mod X a `core.ini` of the test's, which
  moves its plugin list, plugins, modules, configs and logs into
  `cstrike/addons/xen/test`. On the command line alone they would be undone:
  AMX Mod X reads `core.ini` after it. The modules are copies, and
  `xen_amxx.dll` among them is `runtime/build`'s - the build under test -
  while the running server keeps its own;
- `+localinfo xen_plugins addons/xen/test/plugins.ini` gives the Xen module a
  plugin list of its own. Plugins are looked for in `plugins/` beside the
  list, and the module does not lay out `addons/xen` for such a server;
- hlds writes its console log (`-condebug`) into its working folder, where the
  running server writes its own. So the test server runs in `xen-test` beside
  `hlds.exe`, a folder of junctions to `cstrike`, `valve` and `platform`: hlds
  finds the game where it expects it, and the log is the test's;
- it is stopped by its process id, never by name, and both folders are
  removed at the end.

Before starting, the runner refuses a port some hlds already has. Once the
server is up it checks that AMX Mod X runs only the test's plugins and that
the Xen module took the test's list; if not, it stops there.

### Writing a suite

A suite is a plugin in `tests/server/`: a `.ts` built like one in `as/` (with
`~/`), or a `.sma` compiled with `amxmodx/base/amxxpc.exe` against the
includes the `.ts` suites export and the repository's `includes/` (reapi,
`nhnse_const.inc`). It never goes into the server's own plugin
list. It registers a server command `xen_test_<name>` and logs its checks with
`Checks` from `~/lib/check`, made without a player:

```ts
import { Cvar, server } from "~/facade";
import { Checks } from "~/lib/check";

const answer = new Cvar("xen_test_answer", "42");   // at the top level on purpose

server.addServerCommand("xen_test_cvar", (args) => {
	const check = new Checks("cvar");
	check.expect(answer.value, "значение по умолчанию").toBe("42");
	check.done();                                    // [cvar] N ok, M failed
});
```

- The tag is the command's tail with `_` written `-`:
  `xen_test_universal_config` logs as `[universal-config]`. A Pawn suite
  prints the same lines itself, with `server_print`.
- The runner waits 20 s for `[<name>] N ok, M failed`, so an async suite calls
  `check.done()` when it is done, not when the command returns.
- A line `// @log <text>` in a suite is text the console has to show while it
  runs. It is looked for as written - `// @log Привет, мир` fails when
  Cyrillic arrives as question marks - and an error line the suite causes on
  purpose (a trap in a coroutine) does not count as an error.
- A suite that needs a player uses a bot: the runner makes sure one is on the
  server (`yb add`), and `amxclient_cmd(bot.id, "say", "/cmd")` types a chat
  command for it.
- A plugin a suite needs besides itself (`as/universal-config.ts`) is listed
  in `EXTRA_PLUGINS` in `scripts/test-server.ts`; a file the suite reads goes
  in `tests/server/fixtures/` (copied into the test server's configs); an
  argument from the runner goes in `SUITE_ARGS`.

The suites: `cvar` (a `Cvar` at the top level - `create_cvar` during
`plugin_natives` used to crash the server), `entity` (`entity.origin`, then
`Entity.findAll({ near, radius })` - the engine relink), `time`
(`Date.now()`, `performance.now()`, `Math.random()` - the i386 `_alldiv`),
`async` (sleep order, abort, a trap dropping one coroutine), `utf8`
(Cyrillic in the console and through a native), `player` (a bot's chat
command), `natives` (a Pawn plugin calling a TypeScript plugin's natives:
strings, `Float`, arrays, out-buffers), `universal-config` (its natives on
`fixtures/xen-test.ini`), `menu-core` (a Pawn suite: a menu with a Pawn and a
TypeScript placeholder, a list data source row and lang keys shown to a bot
with `lang ru`, read back with `mc_get_menu_text`; `menu-ts.ts` serves the
TypeScript placeholder), `menu-lang` (`LookupLangKey` in the bot's language
and in the server's) and `nhnse` (a Pawn suite compiled against the
generated `nhnse_core.inc`, as the nhnse modules are: core.ini's cvars, the
natives answering as the modules call them - out-buffers, `&ref`, `%L` -
`chooseteam` opening the main menu for a bot, and a restart raising
`nhnse_on_round_start`). universal-config, menu-core and nhnse-core are
loaded for every run (`EXTRA_PLUGINS`), with `fixtures/nhnse/core.ini` and
`menu.ini`; the config folder is one for the whole server, so a suite that
reads its own files sets it (`cfg_set_base_dir("")`).

It needs `XEN_SERVER` in `.env`, the module built (`runtime/build`), the host
plugin (`runtime/host/xen_host.amxx`) and YaPB on the server for the bot.
