In the plugin that owns the module this is the module. In any other plugin
the build puts a proxy in its place: the same functions and types, each call
running in the owner. So a menu has the items every plugin added, a player has
one open menu, and the config folder is one for the whole server — whoever
set it. The plugin's code, and what its editor shows, is the same either way.

A module file of a project, without a package (`~/modules/http`), is
compiled into every plugin that imports it, as before.

## Who owns a module

The module's plugin: its package's natives (`"amxts": { "natives": ... }`),
or — for a module without natives — the plugin the build makes for it. The
build names it after the package — `menu-core.aot` for `@amxts/menu-core` —
and puts it in `plugins.ini` before the project's plugins, after the modules
it requires. A module file in the plugins folder, `modules/<name>.ts`, is
owned by the plugin of the same name there, `<name>.ts`, when there is one;
on a server, where a plugin is compiled from the plugins folder, a
`<name>.aot` there counts too.

A call made while the owner is not running fails with a line in the log
(`~/modules/menu-core: no plugin runs it — is menu-core.aot in
plugins.ini?`) and returns nothing — `false`, `0`, `""`, `null`.

The owner registers the module while its top level runs, so a plugin listed
before the owner in `plugins.ini` can call it from
`server.addEventListener("init", ...)` and later, not from its own top level.
The build's order puts every owner first.

## What crosses

| In the module | Between plugins |
| --- | --- |
| `number`, `boolean`, `string`, a union of strings | as they are |
| `T[]`, `T \| null` | as they are |
| `Player` | by its id |
| an object the module hands out and takes back (`Config`, `Section`), or hands out with methods of its own (`Menu`) | the owner's object: its fields are read and written there, and its methods run there |
| any other object — an interface (`MenuShowOptions`, `ListRow`, `SectionEntry`), a class of fields | a copy; a field left out stays left out |
| an object with methods (`MenuEvent`) | a copy, and after the call its fields come back: `event.preventDefault()` works |
| a function (`ConditionTest`, `onSelect`, a list source) | stays where it was written; the other side calls it back |

"Handed out and taken back" means an exported function returns it and
another takes it (`load()` returns a `Config`, `section(config, ...)` takes
one); a class with methods of its own is enough to be handed out
(`create()` returns a `Menu`, and `menu.addItem(...)` runs in the owner).
Such an object is the same object in every plugin: `find("X")` twice is the
same `Menu`, `menu.title = "..."` changes the owner's menu, and a function
given to one of its methods - `onSelect` - is called back where it was
written. Its private fields stay in the owner, and a `readonly` one cannot be
set from another plugin either.

A function passed across stays one function: registering the same one twice
passes the same one, so a module can compare it.

## What does not, and says so

The build stops, naming the module, the function and the parameter, when an
exported function of a module that has an owner:

- takes or returns a type that cannot cross — a `Map`, a `Set`, a generic
  class, a class from the standard library, a type the module does not
  export;
- has a default the other plugin cannot evaluate — `index = base`
  (a literal, `{}`, `[]`, `null` are fine);
- is generic, async, or has a rest parameter;
- is an exported variable (`export let count`): export a function that reads
  or sets it;
- hands out and takes back a class with methods.

```
~/modules/bad: export function remember - parameter "counts": Map from the standard library cannot cross - pass its contents as an array or a record
```

## Limits

- A field of a shared object that is an array or an object is read as a copy:
  `menu.items.push(item)` changes the copy. Assigning the field
  (`menu.items = items`), or the module's own function (`addItem`), changes
  the owner's.
- Every call copies its arguments both ways and goes through the module: far
  dearer than a call inside one plugin. Reading a whole file section by
  section at start-up is fine; a call per player per frame is worth avoiding.
- The owner and the plugins that call it are built from the same module
  source: after changing it, build them all (the `plugins` and `dev`
  scripts do). A plugin built against another version gets a line in the log
  instead of a call.
