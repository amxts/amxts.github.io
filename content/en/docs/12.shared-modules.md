A module under `as/modules/` that has a plugin of the same name - the
menu-core plugin `as/menu-core.ts` and `~/modules/menu-core`, the
universal-config plugin and `~/modules/universal-config` - has **one instance
on the server**, that plugin's. Every plugin writes the same import:

```ts
import * as menus from "~/modules/menu-core";
import * as ini from "~/modules/universal-config";

menus.addCondition("IS_ALIVE", (player) => player.isAlive);
menus.addAction("RESET_SCORE", (player) => resetScore(player));
menus.show(player, "MAIN_MENU", { resetHistory: true });

const menu = menus.find("MAIN_MENU");
if (menu != null) menu.hideExit = true;

ini.setBaseDir("nhnse");
const main = ini.section(ini.load("core.ini"), "MAIN");
```

In the plugin that owns the module this is the module. In any other plugin
the build puts a proxy in its place: the same functions and types, each call
running in the owner. So a menu has the items every plugin added, a player has
one open menu, and the config folder is one for the whole server - whoever
set it. The plugin's code, and what its editor shows, is the same either way.

A module without a plugin of its name (`~/modules/http`) is compiled into
every plugin that imports it, as before.

## Who owns a module

The plugin whose file has the module's name: `as/<name>.ts` owns
`as/modules/<name>.ts`. On a server, where a plugin is compiled from the
plugins folder, a `<name>.aot` there counts too. The owner has to be in
`plugins.ini`; a call made while it is not running fails with a line in the
log (`~/modules/menu-core: no plugin runs it - is menu-core.aot in
plugins.ini?`) and returns nothing - `false`, `0`, `""`, `null`.

The owner registers the module while its top level runs, so a plugin listed
before the owner in `plugins.ini` can call it from
`server.addEventListener("init", ...)` and later, not from its own top level.

## What crosses

| In the module | Between plugins |
| --- | --- |
| `number`, `boolean`, `string`, a union of strings | as they are |
| `T[]`, `T \| null` | as they are |
| `Player` | by its id |
| an object the module hands out and takes back (`Menu`, `Config`, `Section`) | the owner's object: its fields are read and written there |
| any other object - an interface, a class of fields (`MenuShowOptions`, `ListRow`, `SectionEntry`) | a copy |
| an object with methods (`MenuEvent`) | a copy, and after the call its fields come back: `event.preventDefault()` works |
| a function (`ConditionTest`, `onSelect`, a list source) | stays where it was written; the other side calls it back |

"Handed out and taken back" means an exported function returns it and
another takes it (`create()` returns a `Menu`, `addItem(menu, ...)` takes
one). Such an object is the same object in every plugin: `find("X")` twice
is the same `Menu`, and `menu.title = "..."` changes the owner's menu.

A function passed across stays one function: registering the same one twice
passes the same one, so a module can compare it.

## What does not, and says so

The build stops, naming the module, the function and the parameter, when an
exported function of a module that has an owner:

- takes or returns a type that cannot cross - a `Map`, a `Set`, a generic
  class, a class from the standard library, a type the module does not
  export;
- has a default the other plugin cannot evaluate - `index: number = base`
  (a literal, `{}`, `[]`, `null` are fine);
- is generic, async, or has a rest parameter;
- is an exported variable (`export let count`): export a function that reads
  or sets it;
- hands out and takes back a class with methods.

```
~/modules/bad: export function remember - parameter "counts": Map from the standard library cannot cross - pass its contents as an array or a record
```

## Limits

- A field of a shared object that is an array or an object is read as a copy:
  `menu.items.push(item)` changes the copy. Assigning the field
  (`menu.items = items`), or the module's own function (`addItem`), changes
  the owner's.
- Every call copies its arguments both ways and goes through the module: far
  dearer than a call inside one plugin. Reading a whole file section by
  section at start-up is fine; a call per player per frame is worth avoiding.
- The owner and the plugins that call it are built from the same module
  source: after changing it, build them all (`bun run plugins` and `bun run
  dev` do). A plugin built against another version gets a line in the log
  instead of a call.

## Under the hood

- `scripts/shared-modules.ts` compiles the module on its own with asc, before
  the plugin (asc is not reentrant): its exported functions are compiled as
  exports, so the result types the compiler inferred and every field of every
  type are known. From that it writes the proxy, which the plugin's compile
  reads in place of the module file, and, for the owner, a dispatcher parsed
  beside it (`__xen_serve.ts`) that runs each call on the real module and
  registers it under the module's name. A hash of what crosses is in both,
  and the module compares them.
- `as/remote.ts`: the byte buffers, the plugin's table of functions others
  call back, the owner's table of objects it handed out, and the export the
  module calls, `__xen_rpc`. A function received is a stand-in with the same
  signature whose `_env` holds where it calls - the mechanism promises use
  (`__co_bindEnv`), which the compiler supports on every indirect call once
  the build asks for it.
- `runtime/src/module.cpp`: `xen_serve`, `xen_owner`, `xen_rpc` and the three
  that move the bytes (`xen_rpc_take`, `xen_rpc_reply`, `xen_rpc_result`). A
  call runs in the target plugin like an event handler does; a call inside a
  call - a condition asked while a menu is drawn - is a call like any other.
